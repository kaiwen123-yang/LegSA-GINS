# 06 航向与垂向机制小试验：完成结果

本轮支持一个有限结论：独立 body 速度辅助对“航向来源中断、位置和速度仍可用”的情形有一定帮助；加入第三维速度能够显著减轻垂向漂移，但同时进一步损害 D61/D62 的水平误差。**垂向获得了候选机制证据，D62 的水平退化没有解决。M3 不应替代原 V3，也不宜作为默认升级。**

全部算法构建、检查、solver 与 evaluator 在 E 盘 Ubuntu 22.04 WSL 内完成。正式 C++、原 V3 和既有 payload 未修改。完整设计见 [冻结合同](PILOT_CONTRACT.md)、[T02 预注册](PILOT_PREREGISTRATION.json) 和[独立审查](05_INDEPENDENT_REVIEW.md)。

## 试验身份与支持

- M0：10 月 4 日诊断版本，GNSS 事件触发 RP/HV，旧 HV 依赖外部 A1 航向构造。它不是原 V3 的新一轮验证。
- M2：上一轮候选，RP 和二维 body 速度独立、因果触发；测量构造不依赖 A1。
- M3：在 M2 上增加 SDK body-z，三维同用预先冻结的数值标准差 0.132838 m/s，无参考调参。SDK 坐标系、物理点与三维协方差尚未独立标定。
- C00 是正常全窗；D61 为完整 GNSS 信息中断；D62 保留双天线航向；H20 只中断航向来源并同步关闭其派生的旧 HV，GNSS 位置、接收机速度和 Doppler 保留。各故障注册区间均为 [196.2,216.2)。
- H20 旧 HV 必须去除 A1 插值支持，因此旧 HV 实际不支持区间为 (196,217)。不能把 H20 简写为只关闭滤波器航向开关。

新增六组成对结果，复用六组已封存结果，不重新执行旧 solver/evaluator。新旧共十二组 NAV 时间键和 evaluator 时间键逐项完全相同。每组 NAV 56,642 行；故障评分 3,678 个共同样本，196.201064–216.197081 s。最后一项是最后有支持样本，**不是精确 216.2 s 终点**。

## 航向收益有多少

H20 中 M2 相对 M0 的 yaw RMSE 下降 0.585972°（23.54%），但这不能全部归于抗航向缺测：M2 在正常状态本来已有较低 yaw 误差。用每种模式自身的 C00 同时间窗作反事实对照：

| 模式 | C00 同窗 yaw RMSE | H20 yaw RMSE | 缺测增加量 |
|---|---:|---:|---:|
| M0 | 2.196709° | 2.488925° | +0.292215° |
| M2 | 1.769082° | 1.902952° | +0.133870° |
| M3 | 1.761616° | 1.893358° | +0.131742° |

M2 的缺测增加量比 M0 少约 0.158345°；M3 在这方面只再少约 0.002128°。这是可见但有限的单次事件证据，不能用完整 GNSS 丢失时的大幅水平改善代替航向论证。详见 [同窗控制 CSV](H20_SAME_WINDOW_CONTROL.csv)。

机制也应限定：H20 保留 NED 速度与位置，机器人在运动时，body 速度和导航系速度的相对方向能够间接帮助航向。当所有外部水平参照都消失，同时旋转全球 yaw 和水平速度仍保持 h=Rᵀv 不变，因此 body 速度不凭空产生绝对航向。低速、静止、无初始 heading 或接触滑移没有由本试验得到解决。

## 垂向改善说明什么，D62 如何处理

M2 没有第三维 body 速度观测。加入这一行后，D61 垂向 RMSE 从 7.126477 降至 0.634415 m（相对 M2 下降 91.10%）；D62 从 7.122955 降至 0.637321 m（下降 91.05%）。这支持“缺少第三维速度约束参与了垂向漂移”的候选解释。

代价同样明确：D61 水平 RMSE 相对 M2 增加 49.01%；D62 增加 54.81%。D62 原先 M2 比 M0 差 6.52%，现在 M3 比 M0 差 64.91%。M3 虽然显著降低 3D 总误差，但没有通过水平性能要求；只突出 3D 改善会掩盖退化。

本轮尚不能确定水平代价来自哪一项：SDK z 与无滑移足端代理约 4 cm/s 的均值差（尚非真实偏差证明）、SDK 到 IMU 点位差、姿态与速度交叉项、接触滑移或未校准的三维噪声/相关性都有可能。有限差分已检查观测 Jacobian 的数学符号，不能据此认定物理测量模型也正确。不能承诺多调几个参数就会修好。

可执行的后续路线是先明确坐标和物理点、时间对齐及 z 误差来源，再为 contact/运动学速度建立各方向协方差与滑移拒绝，最后在冻结的独立序列检验是否同时守住 H 与 yaw。若只有 SDK 速度且这些边界未闭合，应继续保留条件性辅助的定位，优先维护原 V3 的论文主线，而不是默认打开 M3。

## 关于“是不是全程 FIX”

FIX 是接收机载波解标签，不是 EKF 传播状态的类别。实际输入 join 已完成，不能只凭“native 没有 FIX 字段”作答：

- BY2 主窗 1,370 个输入时刻和 BY2H 主窗 1,350 个输入时刻均双 FIX。
- BY2O 主窗共 1,885 个输入时刻，其中 1,594 双 FIX，另 291 个为 GNSS1 FIX、GNSS2 FLOAT。
- 这 291 个时刻，position 与 receiver velocity 输入仍有效，dual-yaw 输入关闭。当前天然主窗没有 GNSS1 自身 FLOAT 的位置/速度样本，因此没有其质量验证证据。
- IMU 状态继续传播；初始化仍依赖共有的双天线初始航向。本试验没有把 FLOAT 冒充 FIX，也没有放宽原 yaw 门。

因此，“数据都是双 FIX”对 BY2/BY2H 主窗成立，对 BY2O 不成立；“第二天线不是 FIX 就没有导航输出”不成立；“已经验证主天线 FLOAT 的定位效果”也不成立。完整计数与源哈希见 [PROVIDER_FIX_COUNTS.csv](PROVIDER_FIX_COUNTS.csv)。

仓库其他日期的数据另有实证：[R5 NMB输入准入](R5_FLOAT_ADMISSION_NOTE.md)在四段实际native窗口内包含636个GNSS1 FLOAT及167个OTHER_VALID历元，position/RV有效、yaw无效。该结论是既有provider准入，不是本轮候选已完成FLOAT分层精度验证，也不重复计为新导航运行。

## 运行完整性、计数和范围

T02 六次 solver 全部封存后，才执行六次 offline evaluator，各一次 reference 打开，审计及一致性检查全部通过。新六组在线 reference 读取为零。reference 是共享 GNSS 来源的商业融合结果，不能称独立真值。

候选全窗独立 HV 接受 1,369 次，通用 velocity counter、source trace 总接受数和独立事件计数一致。M3 source trace 的实际 dof/active_dimensions 都为 3，horizontal-only counter 为 0；有效 vertical_disabled=false。历史 RUN_MANIFEST 中某些名称仍为 horizontal transport，因此科学身份以专用 run ID、ENV 模式、有效维度及源码/binary pin 联合解释，不能把 M3 冒称旧正式二维方法。

故障窗按 AID_EVENTS 的 state_time 计，M2/M3 各接受 100 个独立 RP 与 100 个独立 HV；H20 M0 的旧 HV 在故障期没有更新。SOURCE_AWARE_WEIGHT_TRACE 的 time 是源采样时间，边界可计入 101 个 RP/HV；汇总明确区分这两种时间口径，不把它们当成重复更新。每组 275 个全窗协方差快照，其中注册故障窗 20 个；15 个有效状态有限、对称并通过 PSD 检查，六个固定 scale 状态保持零。

本轮真实 solver 调用共 7 次：一次已完成整窗传播、因旧 horizontal counter 身份检查而在输出前拒绝；修复检查后六次成功。首次失败未写 NAV/STD、未评估，不能归为 pre-input 失败。原尝试保留，T02 只改变隔离 runtime 身份判据，导航数学源码不变。另有三次配置检查进程、三次 C++ 单元检查进程；这些不是 scientific solver。执行冻结提交为 e5a3c412f2690b771402dc87555ec8e9e05e469d。

这仍是一个 BY2、固定 20 s 事件、固定参数的小试验。当前证据支持继续检查测量模型，不能宣布部署通过、统计泛化、完整足式里程计或新模糊度固定算法完成。
